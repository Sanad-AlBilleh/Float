# Architecture Decision Records

These are my five main decisions. I wrote each one on the day I made it (1, 2 and 3 October 2026). On 4 October I rewrote them in the format the assignment asks for and in simpler words. The decisions did not change.

## 1. Python, FastAPI, Jinja2 and SQLite in one process
Date: 2026-10-01
Status: Superseded by 6
Context: Float has to start from a fresh clone with one command (`python app.py`), save its data in SQLite and run as one process. I also have to explain the code on paper, and Python is the language I know best.
Decision: I used FastAPI to serve both the HTML pages (built with Jinja2 templates) and a JSON API, all from one Uvicorn worker. I talk to SQLite with Python's built-in `sqlite3` module and write the SQL myself. Passwords are hashed with the built-in `hashlib.scrypt`, so the app needs only 4 packages to run (FastAPI, Uvicorn, Jinja2, python-multipart) plus 4 for testing.
Alternatives considered: Django comes with an ORM, an admin site and logins that I mostly would not use, and the ORM hides the SQL I need to understand. Flask is about the same size as FastAPI but does not check request data with types or make API docs for me. A React front end with a separate API would mean two processes, which the assignment does not allow. SQLAlchemy would save me some SQL, but my money rules are easier to see in plain SQL.
Consequences: I can see and test every query, and the pages are plain HTML forms with no JavaScript at all. SQLite only lets one write happen at a time, but that is fine for one flat of students: the dashboard took 48 ms with 16,000 transactions.

## 2. Domains that never import each other, joined by an application layer
Date: 2026-10-01
Status: Decided
Context: The assignment wants at least two parts of the backend that could become separate services later. Some actions touch more than one part. For example, paying a bill changes Planning (the bill) and the Ledger (the expense), and confirming a settlement writes into two people's ledgers.
Decision: I split the code into five packages: Identity, Ledger, Planning, Households and Insights. Other code can only use a package through its `api.py` file, and a test (`tests/test_architecture.py`) fails if one package imports another. The only exception is Insights, which may read the others through their `api.py` because it only does calculations. Actions that touch more than one package live in `app/application/` and run inside one database transaction that also writes an audit record.
Alternatives considered: One big package with shared models would be faster to start, but nothing would stop Planning from reading the Ledger's tables, so the separation would only exist on paper. Real separate services would need network calls between them, which the one-container rule does not allow.
Consequences: Paying a bill or confirming a settlement either fully happens or does not happen at all. The application layer is where I would cut the app apart later: if Households became its own service, those functions would turn into API calls. The packages still share one database and a few foreign keys, which is the price of keeping everything in one app.

## 3. Database: money in cents, strict tables, and payment links instead of "paid" flags
Date: 2026-10-02
Status: Superseded by 7
Context: Every number Float shows comes from rows in the database. A rounding error, a bill saved twice, or a "paid" flag that does not match the real expense would make the safe-to-spend number wrong.
Decision: All money is stored as whole cents (`INTEGER`) in `STRICT` tables, with `CHECK` rules that limit amounts to €1,000,000. A bill counts as paid only when its `paid_transaction_id` points at the expense that paid it, and that column is `UNIQUE` so one expense can only pay one bill. Each bill date is stored once per series (`UNIQUE (series_id, scheduled_date)`). Triggers stop anyone from changing a goal movement, or changing or deleting an audit record. Rows that people edit have a `version` number so two edits at the same time cannot overwrite each other.
Alternatives considered: Floating point numbers (REAL) can round wrongly, for example 0.1 + 0.2 is not exactly 0.3. A `status` column saying "paid" is simpler but can say "paid" when the expense is missing. Working out bills on the fly without saving them would leave nowhere to store an edited amount or a payment.
Consequences: Paying, undoing and splitting a bill are each one transaction, and creating bills again can never make duplicates. Reading is a little slower because Float works out each bill's status and adds up goal movements, but that is fine at a student's scale. Planning cannot move to its own database without replacing its foreign key to the `transactions` table.

## 4. Testing: pure functions, property tests, a real SQLite file and planted bugs
Date: 2026-10-03
Status: Decided
Context: Float is only useful if its numbers are right, and money bugs hide in cases I would not think to test by hand, like odd amounts, ties, many flatmates or long chains of actions. The assignment asks for 70% coverage of the core logic, but coverage only proves a line ran, not that it is right.
Decision: I put every calculation in a pure function (no database) and tested it against the worked examples in the SRS (Fixtures A to G). I used Hypothesis to try many random inputs for rules that must always hold: splits add up to the exact amount, household balances add up to zero, and paying a bill does not change safe-to-spend. Everything that touches the database is tested on a real temporary SQLite file. After each feature I planted small bugs in the code (like changing `<` to `<=`) to check that a test fails.
Alternatives considered: Only hand-written examples would have missed bugs the planted bugs found, like a bill due exactly on payday. Faking (mocking) the database would not test the constraints and triggers my correctness depends on.
Consequences: The 604 tests run in under a minute with nothing else installed, and cover 97% of the business code. I tested the HTML templates and CSS less, because they hold no money logic. I checked them with page tests and by looking at the app in a browser.

## 5. Not built: a background scheduler
Date: 2026-10-03
Status: Decided
Context: Some features depend on time passing. Recurring bills have to exist before they are due, and an alert should show up when a bill is close. The usual answer is a cron job or a background worker.
Decision: Float has no scheduler. When a page needs bills, `ensure_materialized` creates any missing bill dates with `INSERT ... ON CONFLICT DO NOTHING`, so running it twice is harmless. Alerts are worked out again when the dashboard or alerts page opens and after every change.
Alternatives considered: Cron or Celery needs a second process and a message broker, which the assignment does not allow. A scheduler thread inside the app would write to SQLite at the same time as user requests, which causes locking problems, and it does nothing while the app is off anyway.
Consequences: Nothing happens while nobody is using Float, so an alert appears the next time someone opens the app, not at an exact time. There are no emails or push notifications. If I ever need them, a scheduler could call the same functions without rewriting them.

## 6. The split: a personal service and a households service, cut where ADR-2 said
Date: 2026-11-18
Status: Decided
Context: Assignment 2 asks for exactly two services, one per feature domain, each with its own container and its own database, talking over HTTP. Float has five packages (Identity, Ledger, Planning, Households, Insights). ADR-2 already named the cut: "if Households became its own service, those functions would turn into API calls". The hard parts were the places where A1 joined Households with the rest in one SQLite transaction: a shared expense also writes the payer's ledger row, a confirmed settlement writes into two ledgers, the dashboard reads each user's household balances and bill shares, and every household page shows member names from Identity.
Decision: I made two services. **personal** keeps Identity, Ledger, Planning and Insights, and **households** keeps the Households package with its application code (memberships, shared expenses, settlements, household bills, the household activity feed). Insights stays in personal because safe-to-spend is a personal number; it gets the household terms over HTTP. Four things cross the seam, all server side, all with a 2 second timeout: (1) households calls `POST /internal/transactions` on personal to record the payer's ledger row of a shared expense or a paid household bill, (2) households calls it twice to confirm a settlement, (3) households asks personal for member names and for a user's profile (tracking start, allowance day, categories), and (4) personal asks households for a user's position (bill shares, what they owe and are owed), their shares of shared expenses, and new household events for alerts. Sign-in moved from a cookie to a signed bearer token: personal signs it with `TOKEN_SECRET` (HMAC-SHA256, Python standard library), and households checks the signature and expiry itself, so it never has to ask personal "who is this?". The `/internal` endpoints need a shared `INTERNAL_API_KEY`. The small `shared` package (money, dates, recurrence, errors, tokens) is copied into both services instead of being a shared library.
Alternatives considered: Cutting Ledger away from Planning would have broken the foreign key from a paid bill to its expense and needed a call on almost every page. Putting Insights in its own service would make a third container, which is not allowed. Letting the UI call both services and join the data in the browser (client side) would keep the services simpler, but the assignment needs at least one flow that crosses the seam on the server, and a shared expense must reach the ledger even if the browser closes halfway. For sign-in, households could ask personal to check every token, but then households would stop working whenever personal is down, which breaks the partial-failure rule. A shared Python package for `shared` would need a third build context in both Dockerfiles; copying five small, stable files is easier to explain.
Consequences: ADR-2 held: the seam is exactly where it said, and the application functions that joined the two sides became the HTTP calls listed above. When personal is down, households still shows households, balances and settlements, names fall back to the names saved on the last successful read (migration `002_member_name`, added 21 November) and then to "Member #id", and anything that moves money answers 503 "your ledger is unavailable, nothing was saved". When households is down, the dashboard still shows the personal numbers and says household balances are unavailable, and alerts are left as they were instead of being wrongly resolved. The price is that logging out, a password change and the 48-hour idle limit are only seen by personal: households accepts a token until it expires (14 days at most). Each service's tests replace the other service with a small in-memory stand-in, and the real calls are tested together in the integration test (ADR-9).

## 7. Data and migrations: one SQL Server database per service, numbered migrations, and checks in code at the seam
Date: 2026-11-19
Status: Decided
Context: In A1 all 28 tables were in one SQLite file, created on first start, with foreign keys between every part. Assignment 2 needs one SQL Server database per service, a schema that is changed in place once it holds data, and migrations that run once and are recorded. Some A1 foreign keys now point into the other service's database, where SQL Server cannot check them.
Decision: Each table belongs to one service: users, sessions, categories, transactions, bills, goals, budgets and alerts to personal; households, memberships, invitations, shared expenses and their splits, household bills and settlements to households. Each service has its own `audit_events` and `idempotency_keys`. The A1 migrations 0001 to 0012 became one `001_init.sql` per service in T-SQL, because the SQL Server databases start empty: the A1 data was test and demo data only, so nothing was copied across. The rules from ADR-3 stay: money is whole cents (now `BIGINT`, so sums cannot overflow), "paid" is a link to the expense that paid, and edited rows have a `version`. What changed is how they are written: `STRICT` is gone (SQL Server is typed anyway), triggers use `THROW`, the settlement-income rule is a `CHECK` again, dates are `DATE`, and "one expense pays at most one bill" is a filtered unique index, because SQL Server's `UNIQUE` allows only one NULL. Every column that pointed at `users` or `transactions` from the households side is now a plain `INT`. Migrations use my own runner from A1, rewritten for SQL Server: numbered files in `services/<name>/migrations/`, split into batches on `GO` lines, each file and its `schema_migrations` row in one transaction, applied in order at startup. Forward only: an applied file is never edited, a fix is a new file.
Alternatives considered: Alembic or another migration tool would add a dependency and hide the SQL I need to explain; my runner is about 50 lines. Copying the A1 SQLite data would need a one-off export script for data nobody needs. Keeping one database with two schemas would be cheaper, but the assignment asks for one database and one login per service, and a shared database makes it too easy for one service to read the other's tables.
Consequences: What the database no longer guarantees at the seam, the code now does. A shared expense must point at a real ledger row: households creates the row first through `POST /internal/transactions` with an idempotency key, then saves the expense, and deletes the row again if its own write fails. Edits and deletes of ledger rows happen last, just before COMMIT, so a refusal rolls the household change back. A user ID in a membership is trusted because it came from a signed token or from personal. Two things are deliberately not enforced: a category on a shared expense is checked only when the expense is recorded (a user's custom category could be deleted later), and a deleted user would leave household rows behind (Float has no account deletion). If personal saves the row but its reply is lost (a timeout), households sends the same request again once with the same key, and personal answers with the row it already saved, so the ID is known and the row can still be undone. The undo also runs if households' own COMMIT fails (added 21 November after a review). If both tries time out, or the service crashes between the ledger call and the undo, a ledger row could still be left without its expense; a nightly reconciliation job would fix that, but it is out of scope (no background jobs). Recovery plan for a bad migration in production: because each file runs in one transaction, a migration that fails leaves nothing behind and the new container never starts, so CD's health check fails and the old data is untouched. I fix it with a new numbered file and merge again. If a migration succeeded but damaged data, I stop deploying (revert the merge), restore the database with Azure SQL's point-in-time restore into a new database from before the deploy, compare it with the damaged one, and copy the correct rows back with a new migration. A down-migration is never run against production.

## 8. Serverless hosting on Azure: Container Apps that scale to zero, serverless SQL on the free offer, and a static UI
Date: 2026-11-21
Status: Decided (the resources are scripted in `infra/azure-setup.sh`; the first deploy is waiting on the Azure for Students subscription, see README)
Context: Assignment 2 asks for both services, both databases and the UI on Azure, on an account that must not cost money. Float has a handful of users, mostly idle. Whatever runs all day costs money all day, and anything idle has to come back when someone opens the app.
Decision: Each service is one Azure Container App in one Consumption environment, with 0.25 vCPU and 0.5 GiB, **0 to 1 replicas**, so an idle service costs nothing and wakes on the first request. Both databases are serverless Azure SQL (General Purpose, 0.5 to 1 vCore) on the free offer, set to auto-pause when the free monthly allowance runs out instead of billing. The UI is plain files in a Storage account's static website (`$web`), with `config.js` written by CD to point at the two Container App URLs. Images go to GHCR, tagged with the commit SHA. Startup applies the service's migrations (ADR-7) before it takes traffic; with at most one replica they can never run twice at once. Cold starts are handled at three levels: the database connection retries on Azure SQL's "database is resuming" errors (40613 and the TDS connect errors) with doubling waits for about two minutes, `/health` answers 503 until a real query works, and the UI retries a failed call after 3, 8, 15 and 25 seconds behind a "Float is starting up" banner. Errors the services return on purpose (a 503 "Ledger unavailable") are shown, not retried. Secrets (database passwords, `TOKEN_SECRET`, `INTERNAL_API_KEY`) are Container Apps secrets referenced with `secretref:`; GitHub holds them as encrypted secrets and logs in to Azure with OIDC, so no Azure password is stored anywhere.
Alternatives considered: App Service has no scale to zero on a free plan, and its free tier sleeps without a cold-start story I can control. Azure Container Instances run all the time and are billed per second. A provisioned (DTU) SQL database is billed every hour even when idle. Serving the UI from one of the services would tie the UI's availability to that service, which breaks the partial-failure rule (ADR-6). Bicep or Terraform would describe the same resources declaratively, but for nine resources made once, a commented script of `az` commands is easier to read and to mark.
Consequences: The first request after an idle period is slow: the container starts in a few seconds, and a paused database can take up to a minute to resume, which is what the retries and the banner are for. Cost is zero while the free allowances last, and the database pauses rather than charging when they run out. Max one replica means no redundancy: a crashed container is restarted by Azure, but requests fail until it is back. At 100 times the traffic I would change four things: allow more replicas and move migrations into a separate Container Apps job that runs once per deploy (two replicas starting together would both try to migrate); keep a minimum of one replica so nobody waits for a cold start; move the databases off the free offer to provisioned capacity with connection pooling; and cache member names and positions with a short expiry, because the cross-service calls (ADR-6) would become the busiest path.

## 9. Pipeline and testing: what CI gates on, a cross-seam test against the real stack, and stubs inside each service
Date: 2026-11-20
Status: Decided
Context: Assignment 2 asks CI to test every push, with at least 70% coverage per service, and CD to deploy only a commit CI passed. With two services, a test can either replace the other service with a stand-in or run both for real. Real runs are slower and need Docker; stand-ins can drift from the real service.
Decision: CI (`.github/workflows/ci.yml`) runs on every branch push and pull request, and CD calls it first on `main`, so a commit is deployed only if CI passed on that same commit. It gates on four things. (1) The system description matches the code: `scripts/check_system.py` checks that `system.yaml` lists exactly the environment variables each `config.py` reads and that every endpoint one service calls exists in the other's `openapi.json`; the OpenAPI documents are validated, and each service's document is regenerated from the code and must equal the committed file. (2) Lint (ruff) and the tests of each service, with coverage measured per service and the job failing under 70%. (3) A cross-seam integration test (`tests/integration/test_seam.py`) against the whole compose stack: two users, a household, a shared expense that must appear in the payer's ledger, a settlement that must write both ledgers, then each service stopped in turn. (4) Every Docker image builds. Inside each service the other side is a stand-in (`tests/fakes.py`): a scripted households service in personal's tests, and an in-memory ledger in households' tests that can be switched off or made to fail on the n-th call. Tests always run against SQL Server: a throwaway container started in the job with a password made up for that run, never Azure SQL. Added 24 November, to keep the pipeline short: every job that does not need another runs at the same time. In CI the SQL Server image is pulled and started in the background while Python is installed and the code linted, image builds reuse a layer cache, and a newer push to a branch cancels the older run. In CD the two images are built and pushed to GHCR while CI runs, both Container Apps are deployed at once, and the UI upload and both health checks run side by side after that. The deploy jobs need both CI and the images, so Azure only ever receives an image whose commit passed CI; an image of a failed commit may sit in GHCR, tagged with its SHA, but nothing deploys it.
Alternatives considered: Running only the stand-in tests is fast, but nothing would notice the two services disagreeing about a JSON shape; the integration test and the "every called endpoint exists in the other's OpenAPI" check cover that. Running every test against both real services would make each test slow and every failure hard to place. A GitHub Actions service container for SQL Server would need its password written in the workflow; starting it in a step lets the password be random and masked. Testing against SQLite would be faster but would not catch the SQL Server differences ADR-7 lists, which is where most of the porting bugs were.
Consequences: A bug in one service's logic is caught by its own tests in seconds; a broken contract between them is caught by the OpenAPI check or the integration test. Measured on 21 November: personal 96% (409 tests) and households 91% (228 tests) coverage. Every JSON response a test receives is also checked against the response schema in that service's `openapi.json` (`tests/response_schemas.py`), and every documented response is reached by at least one test, and the integration test passes in about 10 seconds locally. Deliberately not tested: the static UI's JavaScript (I checked every page by hand in the browser, including both services stopped), Azure-only behaviour such as the database resuming from a pause (the retry code is there and the CD health check waits up to five minutes), and load. The stand-ins are a second copy of the other service's behaviour; if the real service changes, a stand-in can keep passing until the integration test fails, which is why that test is a CI gate and not optional.


## 10. Not built: a gateway (backend-for-frontend) in front of the two services
Date: 2026-11-21
Status: Rejected for this assignment
Context: The browser talks to two origins: personal for accounts, the ledger and the dashboard, and households for everything shared. That means CORS on both services, two URLs in `config.js`, and the bearer token kept in the browser's `localStorage`, where any script on the page could read it. A single gateway in front of both would hide all of that.
Decision: I did not build one. A gateway would be a third container, and §1c of the assignment allows exactly two. Each service checks the token itself (households verifies the signature locally, ADR-6), allows only the UI's origin in CORS, and the UI loads no third-party scripts, so the token is exposed to Float's own code only.
Alternatives considered: A gateway or backend-for-frontend (for example nginx or a small FastAPI app) would put the UI and both APIs on one origin, so no CORS, and could keep the session in an `HttpOnly` cookie the page's JavaScript cannot read. It could also join data from both services for a page in one call. Folding the gateway into the personal service would keep two containers but make households unreachable whenever personal is down, which is the failure ADR-6 was designed to avoid.
Consequences: Two CORS configurations to keep right, and a token in `localStorage` instead of an `HttpOnly` cookie. I would add the gateway if Float got more front ends (a mobile app wanting one URL), if pages started needing data joined from both services in one request, or if a security review asked for cookie sessions. It would sit in front of the services without changing them, because they already check every token themselves.
